## 1. 场景与用户（为什么做）

### 1.1 场景
某"双一流"高校图书馆。规模基线：

| 维度 | 数值 |
|---|---|
| 在校师生 | 32,000 人 |
| 馆藏 | 58 万种 / 120 万册 |
| 年借阅量 | 96 万次 |
| 日均借还 | 约 4,000 次（借 + 还），峰值集中在中午与晚间各约一小时，折合峰值约 **30 QPS** |
| 日均检索请求 | 约 60 万次（平均约 7 QPS） |
| 开学/考试周检索峰值 | **1,500 QPS** —— 检索是"人人在用"的操作，3.2 万读者集中刷新书单时会出现这种量级 |
| 热门书目开抢瞬时并发 | 单书目 3 秒内 **200+ 并发借阅请求** —— **这才是超卖的真实成因**：借还整体 QPS 很低（约 30），竞争集中在少数热门书目的同一行库存记录上 |
| 容量设计依据 | 压测与实例数按"检索 1,500 QPS + 借还 200 QPS（相对业务峰值 30 留 6 倍余量）"规划；借还接口的 200 QPS 是**容量目标**，不是业务峰值 |
| 现有系统 | 2013 年单体 Java 系统 + 存储过程，无缓存、无检索优化、单实例部署 |

### 1.2 真实痛点（全部来自现状系统的工单记录）
- **P1 超卖**：开学季热门教材（如《高等数学》），多窗口同时借阅导致 `available_copies` 扣成负数，出现"系统显示可借但书已被借走"，2024 年投诉 37 起。
- **P2 检索慢**：读者搜索"计算机网络 谢希仁"，`like '%关键词%'` 全表扫描 120 万行，平均 2.8s，峰值超时 8s；无分词、无拼音、无相关度排序。
- **P3 单点故障**：借阅服务单实例，一次 Full GC/机器故障导致全馆借还停摆 47 分钟。
- **P4 服务台压力**：读者不会用检索式、找不到书、不清楚借阅规则，服务台日均咨询 260 人次，其中 68% 是重复问题（"我能借几本""怎么续借""在几楼"）。
- **P5 人工催还**：逾期靠馆员每周手工导出 Excel 打电话，人力成本高且触达率低。
- **P6 规则硬编码**：借阅册数/期限/续借次数散落在存储过程和 Java 常量里，改一次规则要发版。

### 1.3 用户角色
| 角色 | 画像 | 核心诉求 |
|---|---|---|
| 读者-本科生 | 大一~大四，手机端为主 | 快速找到书、知道在哪、能不能借、什么时候还 |
| 读者-研究生/教师 | 科研需求，借阅量大 | 主题推荐、批量预约、长借期 |
| 馆员-流通部 | 前台/还书台 | 异常借还处理、催还、预约到馆通知 |
| 馆员-采编部 | 后台 | 书目维护、分类、复本管理 |
| 系统管理员 | 运维 | 规则配置、容量监控、故障快速定位 |
| 智能助手（Agent） | 系统角色 | 7×24 自然语言接待读者，能查真实数据、能替读者办事 |

### 1.4 项目目标（可量化）
- 借阅核心链路 **零超卖**（超卖数 = 0）
- 检索 P99 从 2.8s 降到 **< 300ms**，支持分词/拼音/相关度排序
- 单实例故障 **30s 内无感恢复**，可用性目标 **99.9%**
- 服务台重复咨询量下降 **≥ 60%**
- 借阅规则全配置化，**改规则不发版**

## 2. 业务规则（领域规则，代码与测试共同依据）

### 2.1 读者类型与借阅权限
| 类型 | 代码 | 可借册数 | 借期(天) | 可续借次数 | 单次续借天数 |
|---|---|---|---|---|---|
| 本科生 | `UNDERGRAD` | 10 | 30 | 2 | 30 |
| 研究生 | `POSTGRAD` | 15 | 60 | 3 | 60 |
| 教师 | `TEACHER` | 20 | 90 | 3 | 90 |

### 2.2 借阅约束（全部在 `RuleEngine` 中可配置，落 `rule_config` 表）
1. **库存约束**：`available_copies > 0` 才可借；严格不允许负库存。
2. **册数约束**：在借册数 + 1 ≤ 该类型上限。
3. **信用分约束**：`credit_score < 60` 禁止借阅（可查不可借）。
4. **逾期约束**：存在逾期未还记录时禁止新增借阅。
5. **重复借阅约束**：同一读者对同一 `book_id` 最多同时持有 1 册（复本合并计数）。
6. **续借约束**：该 `book_id` 无预约队列时才能续借；续借次数用尽不可续借；逾期状态不可续借。
7. **预约约束**：`available_copies = 0` 时可预约，队列 FIFO；到馆保留 **3 天**，过期自动出队并通知下一位。
8. **罚金**：逾期 **0.2 元/天/册**，封顶为该册书价；罚金未缴清不可借新书（阈值 10 元）。
9. **信用分**：初始 100；逾期 1 次 -5；预约到馆未取 -3；按时归还 +1；上限 100，下限 0。

### 2.3 状态机
- `borrow_record.status`：`BORROWED` → `RETURNED` / `OVERDUE` / `LOST`
- `reservation.status`：`WAITING` → `READY`(到馆保留中) → `FULFILLED` / `EXPIRED` / `CANCELLED`

## 5. 数据模型（详细 DDL 见 `docs/04-数据库设计.md` 与 `deploy/sql/01-schema.sql`）

| 表 | 作用 | 关键字段 | 关键索引 |
|---|---|---|---|
| `reader` | 读者 | id, card_no, name, type, credit_score, status | uk(card_no) |
| `category` | 图书分类（两级，`parent_id` 为空表示一级分类） | id, code, name, parent_id, sort_no | uk(code) |
| `book` | 书目 | id, isbn, title, author, publisher, category_id, publish_year, price, tags, total_copies | uk(isbn), idx(category_id, publish_year) |
| `book_stock` | 库存（与书 1:1；**扣减唯一入口**） | book_id, total_copies, available_copies, locked_copies, version, updated_at | pk(book_id), idx(available_copies) |
| `borrow_record` | 借阅流水 | id, reader_id, book_id, borrow_at, due_at, return_at, renew_count, status, fine | idx(reader_id,status), idx(book_id,status), idx(due_at,status) |
| `reservation` | 预约队列 | id, reader_id, book_id, queue_no, status, ready_at, expire_at | idx(book_id,status,queue_no) |
| `stock_ledger` | 库存流水（对账/审计） | id, book_id, op_type, delta, before_qty, after_qty, biz_no, trace_id | uk(biz_no), idx(book_id,created_at) |
| `idempotent_record` | 幂等表 | idem_key, biz_type, result_json, created_at | uk(idem_key) |
| `rule_config` | 规则配置 | rule_key, rule_value, reader_type, remark, version | uk(rule_key,reader_type) |

**设计要点**：
- 库存与书目**分表**：书目是读多写少（可全量缓存），库存是高频写（不能放缓存里当唯一事实源）。
- `stock_ledger` 保证"每一次扣减都有据可查"，是排查超卖的兜底手段（`sum(delta)` 必须等于 `available_copies` 变化量）。
- 所有扣减 SQL 必须带 `available_copies >= #{n}` 条件，**任何方案都不允许无约束 update**。

## 6. 多种解决方案矩阵（项目核心亮点）

> 每个问题都必须产出：**问题现象 → 候选方案 → 对比维度 → 选型理由 → 代码落地位置 → 实测数据**。
> 落点文件：`docs/09-多种解决方案对比手册.md`，数据来自 `scripts/bench/` 实测。

### 6.1 P1 并发借阅超卖（库存扣减）
| # | 方案 | 原理 | 优点 | 缺点 | 落地 |
|---|---|---|---|---|---|
| S1 | 单机 `synchronized`/`ReentrantLock` | JVM 内互斥 | 最简单 | 多实例失效 | `LocalLockStockStrategy` |
| S2 | **DB 条件更新**（`where available_copies >= n`） | 数据库行锁 + 条件判断 | 无额外组件、天然正确 | 高并发下锁竞争 | `OptimisticDbStockStrategy` |
| S3 | DB 悲观锁 `select ... for update` | 排他锁串行化 | 语义直观 | 持锁时间长、易死锁 | `PessimisticDbStockStrategy` |
| S4 | 乐观锁 `version` + 自旋重试 | CAS 思想 | 无长事务 | 冲突高时重试放大 | `VersionRetryStockStrategy` |
| S5 | **Redis + Lua 原子预扣 + 异步落库** | 内存原子脚本 | 抗高并发、削峰 | 一致性/丢单风险 | `RedisLuaStockStrategy` + 补偿任务 |
| S6 | MQ 串行化扣减 | 单分区顺序消费 | 彻底串行、可削峰 | 链路长、最终一致 | `MqSerialStockStrategy`（本地用单线程 Dispatcher + 有界队列模拟，生产 RocketMQ 事务消息） |

**选型**：默认 S2（正确性优先、组件最少）；秒杀式抢书活动切 S5；选型可配置 `smartlib.stock.strategy`。
**降级**：S5 检测到 Redis 不可用时自动降级 S2（`DegradeFallback`）。
**验收**：`BorrowConcurrencyTest` 用 200 线程抢 10 册，断言 `available_copies == 0` 且成功借出数 == 10、`stock_ledger` 流水守恒。

### 6.2 P2 海量书目检索
| # | 方案 | 原理 | 实测预期 |
|---|---|---|---|
| Q1 | `like '%kw%'` | 全表扫描 | 基线，120 万行 ~2.8s |
| Q2 | 前缀索引 + 条件裁剪 | 只支持前缀 | ~200ms，但召回差 |
| Q3 | **自研倒排索引**（ngram 分词 + 倒排表 + TopK 堆 + 拼音首字母） | 内存倒排 | 目标 P99 < 100ms，零外部依赖 |
| Q4 | MySQL ngram 全文索引 (`FULLTEXT ... WITH PARSER ngram`) | DB 内建 | ~120ms，写放大 |
| Q5 | Elasticsearch | 专业检索引擎 | ~50ms，运维成本高 |

**横向优化（适用全部方案）**：
- 三级缓存：Caffeine(L1, 5min, 10k) → Redis(L2, 30min) → DB
- **防穿透**：布隆过滤器（书目 ID/标题哈希）+ 空值缓存
- **防击穿**：逻辑过期 + 单飞（互斥重建）
- **防雪崩**：TTL 随机抖动 ±10% + 熔断降级到 DB 直查
- **热 key**：检索词 TopN 结果本地缓存

**选型**：默认 Q3（零依赖、可演示）；数据量 > 500 万或需要复杂相关度时切 Q5（`SearchEngine` SPI，切换只改配置）。
**验收**：`SearchBenchmarkTest` 输出各引擎 P50/P99/QPS/召回率对比表。

### 6.3 P3 单点故障与高可用
| # | 方案 | 落地位置 |
|---|---|---|
| A1 | 服务无状态化（JWT，会话外置） | `TraceIdFilter` + 无状态鉴权设计 |
| A2 | 多实例 + Nginx 上游负载 | `deploy/nginx/nginx.conf`（2 实例，健康检查） |
| A3 | 注册中心 + 客户端负载（Nacos） | `docs/07-部署上线手册.md` + `application-prod.yml` |
| A4 | 入口限流（令牌桶） | `TokenBucketRateLimiter`，网关 + 应用双层 |
| A5 | **熔断降级 + 兜底** | `CircuitBreaker`(CLOSED/OPEN/HALF_OPEN) + `DegradeFallback`（查库存降级为"预计可借"，推荐降级为热门榜，检索降级为 DB 直查） |
| A6 | 幂等 + 重试 + 优雅停机 + 探针 | `IdempotencyAspect`、`server.shutdown=graceful`、K8s readiness/liveness |

**验收**：`kubectl delete pod` / `docker kill` 一个实例，压测流量 0 失败（或 < 0.1% 且 1s 内恢复）；熔断器单测覆盖三态迁移。

### 6.4 P4 Agent 效果与工程化（Agent 侧核心亮点）
| # | 方案 | 说明 |
|---|---|---|
| G1 | 纯 Prompt 直答 | 基线：会编造库存/位置，幻觉率高 |
| G2 | **Function Calling 工具调用** | Agent 必须调工具拿真实数据才能回答事实性问题 |
| G3 | **RAG 检索增强** | 借阅规则/馆藏分布/学科服务知识库，BM25 + 可选向量混合召回 |
| G4 | Plan-and-Execute 多步编排 | 复合任务："帮我借《算法导论》，再推荐两本同类，顺便查我有没有逾期" |
| G5 | 规则路由 + LLM 兜底（混合） | 高频意图走规则（快、便宜、稳），长尾走 LLM |

**工程化护栏**：工具白名单、Pydantic 参数校验、超时(3s)/重试(2)/熔断、`无工具证据不下结论`、低置信度转人工、全链路 `trace_id`、SSE 流式输出、Token 与延迟埋点。
**验收**：`agent-service/eval/run_eval.py` 输出意图准确率、工具选择准确率、参数正确率、端到端成功率、平均延迟。

### 6.5 P5 缓存与一致性
Cache-Aside + 延迟双删 + 版本号校验；库存**永不以缓存为唯一事实源**，缓存只用于查询展示，扣减必须落到 DB 条件更新。文档给出"先删缓存还是先更库"的经典取舍分析。

## 8. 接口契约（后端 / 公共 API）

统一响应体：`{"code":0,"msg":"ok","data":{...},"traceId":"..."}`；分页：`{"list":[],"total":0,"page":1,"size":20}`。

### 8.1 对外开放 API
| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/books` | 检索书目（query/category/publisher/yearFrom/yearTo/availableOnly/sort/page/size） |
| GET | `/api/books/{id}` | 书目详情（含库存、位置、简介） |
| GET | `/api/books/hot` | 热门榜 |
| GET | `/api/books/{id}/similar` | 相似书推荐 |
| POST | `/api/borrows` | 借书（`Idempotency-Key` 必填） |
| POST | `/api/borrows/{id}/return` | 还书 |
| POST | `/api/borrows/{id}/renew` | 续借 |
| GET | `/api/readers/{id}/loans` | 我的借阅 |
| GET | `/api/readers/{id}/credit` | 信用分与权限 |
| POST | `/api/reservations` | 预约 |
| DELETE | `/api/reservations/{id}` | 取消预约 |
| POST | `/api/agent/chat` | Agent 对话（SSE 流式，**由 Agent 服务提供**） |

### 8.2 内部工具 API（仅供 Agent 服务调用，`/internal/agent/**`）
带 `X-Internal-Sign`(HMAC) 与 `X-Trace-Id` 透传；限流与公共 API 隔离。

> **接口与 Agent 工具的口径说明**：本组共 **8 个接口**，其中 **7 个**同时作为 Agent 工具暴露
> （`search_books` / `get_stock` / `borrow` / `renew` / `my_loans` / `get_reader_profile` / `policy_qa`）；
> `reservations` 接口服务于公共 API 与预约流程，**暂不作为 Agent 工具暴露** ——
> 预约意味着"排队等待"的长期承诺，让模型自主发起需要产品侧先定义好确认与撤销体验。
> 第 8 个工具 `recommend` 走 `GET /api/readers/{id}/recommendations`。
> 把这段口径写进契约，是因为评审时出现过"§4.3 说 8 个工具、§8.2 列 8 个接口，
> 但两个 8 并不一一对应"的歧义（见 `docs/reviews/02-概要设计评审纪要.md`）。
>
> **签名算法（Java 与 Python 两侧必须逐字一致，否则联调 401）**：
> ```
> canonical = timestamp + "\n" + METHOD(大写) + "\n" + pathWithQuery + "\n" + bodyUtf8
> X-Internal-Sign      = lowercaseHex(HMAC_SHA256(secret, canonical))
> X-Internal-Timestamp = Unix 秒级时间戳，服务端容忍 ±300 秒
> ```
> HMAC 输出为原始 32 字节的小写 hex（不做 base64）；GET 无 body 时该段为空字符串但换行符保留。
>
> **`pathWithQuery` 必须使用「百分号编码后的原始请求目标」**（服务端即 `getRequestURI() + "?" + getQueryString()`）。
> 例如中文参数要签 `?topic=%E7%BB%AD%E5%80%9F`，而**不是** `?topic=续借`。
> 这一点用真实请求验证过：签编码后串得 200，签解码中文得 401（`code=4003`）。
> 这是一个只在**非 ASCII 查询参数**上才会暴露的集成缺陷 —— 用 ASCII 参数做的联调测试完全看不出问题，
> 因此调用方必须直接取 HTTP 客户端库生成的编码后路径（如 httpx 的 `request.url.raw_path`），
> 不要自己拼一套编码规则。该约定与 AWS SigV4 的"签编码后规范请求"一致。

| 方法 | 路径 | 入参 → 出参 |
|---|---|---|
| POST | `/internal/agent/tools/search-books` | `{query,category,page,size,sortBy}` → `{items[],total,tookMs,engine,degraded}` |
| GET | `/internal/agent/tools/books/{id}/stock` | → `{bookId,title,available,total,queueLen,shelfLocation}` |
| POST | `/internal/agent/tools/borrow` | `{readerId,bookId,idempotencyKey}` → `{ok,borrowId,dueDate,reason}` |
| POST | `/internal/agent/tools/renew` | `{readerId,borrowId}` → `{ok,newDueDate,reason}` |
| GET | `/internal/agent/tools/readers/{id}/loans` | → `[{borrowId,title,dueDate,overdueDays,renewable}]` |
| GET | `/internal/agent/tools/readers/{id}/profile` | → `{readerType,creditScore,preferredCategories[],borrowedCount}` |
| POST | `/internal/agent/tools/reservations` | `{readerId,bookId}` → `{ok,queueNo,reason}` |
| GET | `/internal/agent/tools/policy` | `{topic}` → `{answer,source}`（规则库直答，Agent 的 RAG 数据源之一） |

幂等：`borrow`/`renew`/`reservations` 必须带 `idempotencyKey`，服务端用 `idempotent_record` 表兜底。
