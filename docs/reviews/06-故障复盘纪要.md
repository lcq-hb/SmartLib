## 6. 根因分析

### 6.1 直接原因（技术根因）

**库存扣减 SQL 在"性能优化"变更中丢失了条件约束，且扣减与校验之间存在竞态。**

修复前的问题形态（示意，非完整代码）：

```
-- 问题形态：无可用量条件判断，并发下多个请求都能扣减成功
update book_stock set available_copies = available_copies - 1 where book_id = ?
```

并发竞态时序：

| 时刻 | 请求 A | 请求 B | `available_copies` |
|---|---|---|---|
| T0 | 查询可用量 = 1 | — | 1 |
| T1 | — | 查询可用量 = 1 | 1 |
| T2 | 校验通过（1 ≥ 1），执行扣减 | — | 0 |
| T3 | — | 校验通过（基于 T1 的读结果），执行扣减 | **-1** |
| T4 | 插入 `borrow_record` 成功 | 插入 `borrow_record` 成功 | -1（超卖达成） |

正确形态（蓝图 §5 设计要点强制要求）：

```
-- 条件更新：条件判断与扣减在同一条 SQL 内原子完成
update book_stock
   set available_copies = available_copies - #{n},
       version = version + 1,
       updated_at = now()
 where book_id = #{bookId}
   and available_copies >= #{n}
-- 影响行数 = 0 即视为库存不足，返回业务失败，不隐式重试
```

### 6.2 五个为什么（5 Whys）

| 层级 | 问题 | 答案 |
|---|---|---|
| Why 1 | 为什么热门书被超卖？ | 并发请求都对同一 `book_id` 扣减成功，`available_copies` 被扣成负数 |
| Why 2 | 为什么并发扣减都能成功？ | 库存扣减 SQL 没有 `available_copies >= n` 条件，"校验"和"扣减"是两步且不原子 |
| Why 3 | 为什么这条 SQL 能进入生产？ | 前一日"性能优化"变更重写了扣减方法，走热修复通道直连主干，Code Review 仅按"等价重写"口头确认，未做 SQL 级比对 |
| Why 4 | 为什么 CI 与评审没拦住？ | a) 静态检查规则"无约束 update 即构建失败"只在 Gate-3 评审意见中提出并被登记，**尚未落地到 CI**；b) 并发用例只覆盖了"库存充足"的正常路径，**没有"库存为 1 时两个请求并发争抢"的边界用例** |
| Why 5 | 为什么线上 14 分钟无人发现（10:06 → 10:20）？ | 监控只有"库存 = 0"告警，**没有"库存 < 0"与"流水不守恒"的实时告警**；对账任务按小时级调度，最快也要 1 小时后才能发现 |

**根本原因（Root Cause）**：库存扣减的正确性依赖**应用层两步校验**而非**数据库级原子条件更新**，且该红线缺少"CI 静态强制 + 边界并发用例 + 实时负库存监控"三重防线，导致一次看似等价的 SQL 重写即可突破入口。

### 6.3 防线缺口分析（Swiss Cheese）

| 防线 | 设计意图 | 本次是否生效 | 缺口原因 |
|---|---|---|---|
| 详细设计红线 | 所有扣减必须带条件（蓝图 §5） | 设计文档有，**实现脱离** | 无强制手段，文档约束不落地 |
| Code Review | 发现 SQL 语义变更 | **未生效** | 热修复通道 + 口头"等价重写"确认，无 SQL diff 检查项 |
| CI 静态检查 | 无约束 update 即构建失败 | **未落地** | Gate-3 的 X-07 改进项未按期实现 |
| 自动化测试 | 并发场景断言 | **部分生效** | 有 200 线程抢 10 册用例，但缺"最后 1 册争抢"边界与流水守恒断言（对应 Gate-4 的 E-01 遗留） |
| 运行监控 | 库存异常告警 | **未生效** | 只有"库存 = 0"告警，无负库存与流水不守恒实时告警 |
| 对账任务 | 发现记账不一致 | **延迟生效** | 小时级调度，非实时；本次是对账告警在 10:18 触发，属于**最后一道防线** |
