# SmartLib 阶段门评审体系说明（reviews/README.md）

> 本目录收录 SmartLib 项目**六个阶段门（Gate）评审纪要**，用于展示"完整软件生命周期"的规范化研发流程。
> 技术契约：`docs/00-项目蓝图.md` v1.0.0（唯一事实来源）。
> 本目录所有内容均为**简历项目的模拟项目情境文档**，不代表真实企业会议记录。

---

## 1. 评审体系总览

### 1.1 设计目标

| 目标 | 说明 |
|---|---|
| 流程可追溯 | 每个阶段有明确的准入条件、准出标准、评审意见与结论，形成完整证据链 |
| 决策有依据 | 选型结论必须给出"为什么不用其余方案"，并落到 ADR |
| 质量有门禁 | 关键红线（库存正确性、Agent 事实性、幂等）设为一票否决项，不允许豁免 |
| 问题可闭环 | 每条评审意见都有责任人角色、截止日期与跟踪状态；遗留问题单独成清单 |
| 数据不造假 | 未实测的指标一律写"待实测回填"，禁止编造（蓝图 §7 明确要求） |

## 2. 阶段门定义（Gate Definition）

### 2.1 通用门禁模型

```
[准入检查] → [材料分发 ≥48h] → [评审会：汇报+质询+表决] → [结论：通过/有条件通过/不通过]
      ↓                                                              ↓
[条件项清单]  ←————————————————————————————————————————————  [遗留问题清单]
      ↓
[跟踪表闭环] → [复审（书面或定向会议）] → [状态更新为"通过"] → [进入下一阶段]
```

### 2.2 各门的准入（Entry）与准出（Exit）标准

| 门 | 准入条件（Entry Criteria） | 准出标准（Exit Criteria，来源：蓝图 §10） | 一票否决项 |
|---|---|---|---|
| Gate-1 需求 | 干系人访谈完成；痛点有工单/记录佐证；技术契约蓝图 v1.0.0 已定稿 | 用户故事覆盖 6 大痛点（P1~P6），需求可测试（RTM 覆盖率 100%） | 验收口径缺失（性能/效果类指标无度量方法） |
| Gate-2 概设 | Gate-1 条件项全部关闭；选型矩阵完成初稿 | 接口契约冻结、方案对比有结论、拓扑与部署形态明确 | 触碰库存红线（无约束 update） |
| Gate-3 详设 | 概设条件项关闭；《接口契约冻结确认单》签署 | 接口契约冻结、DDL 可执行、并发与事务设计可验证 | 库存扣减无 DB 约束；Agent 事实性无代码级硬约束 |
| Gate-4 测试 | 编码完成且 `mvn test`/`pytest` 全绿；用例矩阵与脚本就绪 | SLO 达标或说明差距；门禁用例通过；遗留缺陷有处置结论 | 超卖数 ≠ 0；事实性回答有工具证据比例 ≠ 100% |
| Gate-5 上线 | Gate-4 条件项关闭；SLO 判定表双签；回滚与应急预案齐备 | Compose 一键起、健康检查通过；Checklist 全部勾选 | 无回滚预案；明文密钥/口令入库；库存前向修正 SOP 缺失 |
| Gate-6 运维 | 上线运行满一个观测周期；监控与告警生效；迭代路线图草案 | 有演练记录与迭代计划；故障改进项闭环并有验收方式 | 同类正确性缺陷未建立强制防线（CI 无法拦截） |

### 2.3 三种结论的定义与处置

| 结论 | 定义 | 后续动作 | 本项目实例 |
|---|---|---|---|
| **通过（Pass）** | 无致命项，严重项可在下一阶段前闭环 | 直接进入下一阶段 | 各门条件关闭后的状态 |
| **有条件通过（Conditional Pass）** | 存在严重项但已定条件、责任人与截止日期 | 条件关闭前不得进入下一阶段的关键环节；由指定角色书面复审 | Gate-1、Gate-2、Gate-4、Gate-5、Gate-6 |
| **不通过（Reject）** | 存在致命项或准出标准未达成 | 修改后重审（定向复审或全会）；里程碑状态保持"未达成" | Gate-3（含 2 项致命项） |

**严重程度取值**：`致命（Blocker）/ 严重（Major）/ 一般（Minor）/ 轻微（Trivial）`
**类别取值**：`缺陷（Defect）/ 风险（Risk）/ 建议（Suggestion）/ 疑问（Question）`
**处置取值**：`修改（Fix）/ 接受（Accept，记录但暂不修改）/ 驳回（Reject，说明理由）`

## 3. 评审角色与职责

### 3.1 角色矩阵

| 角色 | 在评审中的职责 | 表决权 | 主要产出 |
|---|---|---|---|
| 项目经理（PM） | 主持门禁判定、范围确认、条件与遗留问题的跟踪闭环 | 有 | 决议、待办跟踪表、状态更新 |
| 技术负责人（Tech Lead） | 技术可实现性、架构与红线把关、ADR 决策、契约冻结签署 | 有 | ADR、契约冻结确认单 |
| 后端开发（Java） | 借阅/库存/检索/缓存的实现可行性、并发与事务设计质量 | 有 | 设计细节、代码、CI 检查 |
| Agent 开发（Python） | Agent 效果与工程化护栏、工具契约、评测口径 | 有 | 护栏设计、评测报告 |
| 测试负责人 | **需求的测试性审查**、用例设计、门禁用例、缺陷分级与结论 | 有 | 测试报告、缺陷清单、SLO 判定表 |
| DBA | 数据模型、索引、容量、对账、数据修复方案 | 有 | DDL、对账与修正 SOP |
| 运维/DevOps（Gate-5 主持） | 部署、灰度、回滚、应急、监控告警与演练 | 有 | 上线 Checklist、回滚预案 |
| 系统管理员代表 | 规则配置、容量监控、故障定位能力的需求方视角 | 无 | 配置与告警需求 |
| 流通部/采编部馆员代表 | 业务真实性、现场可操作性、用户沟通与补偿 | 无 | 业务验收意见 |
| 信息安全与合规评审人 | 个人信息最小化、脱敏、内部签名与防重放、密钥轮换 | 无（可书面提出否决级意见） | 合规意见条款 |
| 记录人 | 会议记录、意见编号、跟踪表维护 | 无 | 本目录各纪要文件 |

### 3.2 表决规则

| 规则 | 内容 |
|---|---|
| 表决方 | Gate-5 为五方（PM、Tech Lead、运维、测试、DBA）各一票；其余门为 PM + Tech Lead 双签生效 |
| 否决规则 | 任一表决方否决即为 No-Go/不通过，但必须当场给出解除条件与复审时间 |
| 缺席处理 | 缺席角色须提交书面意见，书面意见与到场意见同等效力并纳入意见表 |
| 记录要求 | 每条意见必须有编号、提出人角色、类别、严重程度、结论、责任人角色与截止日期 |

### 3.3 编号规则（跨文件可追踪）

### 4.1 写作规范（强制）

| 规范 | 要求 |
|---|---|
| 语言与格式 | 中文、Markdown、大量表格；不使用无信息量的套话 |
| 技术细节 | 必须与蓝图一致（组件、版本、表名、字段、接口路径、SLO 目标值） |
| 数据纪律 | **严禁编造实测性能数据**；未实测项写"待实测回填"，测算值须标注为"测算" |
| 意见质量 | 每条意见必须具体到"哪个模块/哪条 SQL/哪个接口/哪个指标"，禁止"建议加强测试"式空话 |
| 差异化 | 每份纪要聚焦本阶段强相关议题（需求=范围与验收；概设=选型与拓扑；详设=锁/缓存/事务/护栏；测试=指标与缺陷；上线=回滚与 Checklist；复盘=时间线与根因） |
| 篇幅 | 每份纪要 ≥ 180 行，含完整表格与签字栏 |
| 一致性 | 跨文件的意见引用使用编号（如"承接 Gate-3 的 X-06"），形成可追溯链 |

## 6. 使用说明

| 场景 | 使用方式 |
|---|---|
| 新增一次评审 | 复制 §4 模板 → 填写会议信息 → 引用蓝图章节 → 逐条编号 → 统计 → 决议 → 跟踪表 → 签字 → 附注 |
| 复审（条件关闭） | 在原纪要中不直接改结论；新增"复审记录"章节或在下一步文档中引用（如 Gate-3 定向复审 → 记录于 `docs/11-架构决策记录ADR.md` 与 Gate-4 纪要前置条件） |
| 意见追踪 | 用编号（`R/C/X/E/G/F`）+ 遗留问题（`OI`）+ 待办（`T`）+ 改进项（`AI`）四层编号交叉引用 |
| 简历讲解 | 每份纪要的"结论 + 关键否决项"即为一个 STAR 故事素材：情境（阶段目标）→ 任务（门禁要求）→ 行动（评审意见与修复）→ 结果（结论与闭环） |
| 面试准备 | 与 `docs/10-简历话术与面试问答.md` 配合，重点准备：为什么默认 S2、缓存能否作为库存事实源、幂等与对账为何缺一不可、无实测如何判定指标 |
